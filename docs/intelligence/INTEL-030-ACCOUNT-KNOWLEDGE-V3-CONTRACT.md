# INTEL-030 — Contrat fonctionnel définitif AccountKnowledge V3

Statut : contrat fonctionnel gelé pour la future version V3 de l’onglet Entreprise.

Portée du Lot 0 : documentation uniquement. Aucun type TypeScript V3, validateur, workflow n8n, callback, loader, RPC, schéma SQL ou composant UI n’est créé ou modifié par ce contrat.

Le flux éditorial de la future étude comporte exactement les sept sections ci-dessous, dans cet ordre. Aucune autre section fonctionnelle ne peut être ajoutée ou intercalée.

## 1. SYNTHÈSE DU COMPTE

Cette section reprend la logique éditoriale de la « Synthèse sectorielle » FOLIO.

Elle doit permettre de comprendre immédiatement :

- les métiers ;
- le positionnement de marché ;
- la taille ;
- la dynamique ;
- le rayonnement ;
- la proposition de valeur ;
- les défis ;
- les opportunités actuelles ;
- les principaux éléments différenciants.

La restitution doit être narrative, dense et synthétique. Elle résume les informations détaillées dans les six sections suivantes, sans introduire de fait qui n’y serait pas étayé.

## 2. FICHE D’IDENTITÉ

Cette section reprend la fiche d’identité actuelle avec la charte graphique FOLIO.

Informations attendues selon disponibilité :

- nom ;
- raison sociale ;
- siège ;
- secteur ;
- segment métier ;
- chiffre d’affaires ;
- effectif ;
- rayonnement géographique ;
- dynamique récente.

Les données relationnelles Supabase restent prioritaires sur les générations LLM. Une valeur relationnelle disponible ne doit pas être remplacée par une reformulation ou une estimation générée.

## 3. POSITIONNEMENT MARCHÉ

Sous-sections obligatoires, dans cet ordre :

### Positionnement du compte

Décrire la place occupée par l’entreprise, les marchés et segments sur lesquels elle se présente et la manière dont elle se différencie.

### Environnement concurrentiel

Décrire la structure concurrentielle utile à la compréhension du compte, sans confondre contexte de marché et concurrence directe.

### Concurrents directs

Identifier les concurrents réellement comparables et sourcer la justification de cette comparabilité.

### Avantages concurrentiels

Présenter les avantages étayés, en distinguant les preuves externes des avantages seulement revendiqués par l’entreprise.

### Opportunités

Présenter les opportunités actuelles démontrables pour le compte, en séparant les faits observés de leur interprétation.

### Menaces

Présenter les menaces étayées qui affectent le positionnement, l’activité ou la capacité de différenciation du compte.

### Politique et ambitions

Cette sous-section synthétise :

- la raison d’être revendiquée ;
- la philosophie ;
- la culture ;
- les prises de parole publiques ;
- les ambitions ;
- les grands axes stratégiques ;
- la posture de dirigeants ;
- l’identité profonde de l’entreprise.

Les discours revendiqués doivent être distingués des faits vérifiés. Une prise de parole institutionnelle est présentée comme déclarative, même lorsqu’elle est publiée sur un support officiel.

## 4. OFFRES ET CLIENTÈLE

### Offres

Cette sous-partie couvre :

- le cœur de métier ;
- les offres principales ;
- les domaines réellement couverts ;
- les prestations ;
- les modèles de service ;
- les activités complémentaires.

### Activités non couvertes

Cette sous-partie recense les activités habituellement rattachées au métier mais non identifiées dans le périmètre public de l’entreprise.

Une absence de preuve ne doit jamais être transformée en certitude. La formulation « aucune offre publique identifiée » est obligatoire lorsque la recherche n’a pas permis d’établir l’existence d’une offre, sans pour autant prouver son absence.

### Clientèle

Cette sous-partie couvre :

- le profil client type ;
- la segmentation ;
- le poids estimé des segments uniquement lorsqu’il est sourçable ;
- les tendances comportementales ;
- les besoins non couverts.

## 5. CHAÎNE DE VALEUR

Sous-sections obligatoires :

### Description

Décrire la chaîne de valeur propre au compte et son articulation générale.

### Proposition de valeur

Expliquer la valeur produite et la manière dont elle est délivrée aux clients.

### Maillons clés

Identifier les étapes, activités ou capacités indispensables au fonctionnement du modèle.

### Partenaires ou fournisseurs critiques

Identifier les tiers dont dépend de manière significative la création ou la livraison de valeur.

### Dépendances

Présenter les dépendances opérationnelles, technologiques, humaines, commerciales ou réglementaires étayées.

### Points de vulnérabilité

Présenter les fragilités démontrables de la chaîne de valeur et distinguer clairement les observations des analyses.

### Relation avec la clientèle finale

Décrire le lien entre les maillons de la chaîne de valeur et l’expérience ou la valeur reçue par la clientèle finale.

## 6. ENVIRONNEMENT RÉGLEMENTAIRE

Cette section contient exclusivement les trois sous-sections suivantes :

### Réglementations en vigueur

Réglementations actuellement applicables au compte ou à ses activités, avec leur impact démontrable.

### Certifications requises

Certifications, qualifications ou agréments nécessaires ou structurants, uniquement lorsque leur caractère requis ou attendu est sourçable.

### Risques de conformité

Risques associés au non-respect des règles ou exigences applicables, en distinguant risque générique et exposition propre au compte.

La rubrique « réglementations à venir » est explicitement exclue de l’onglet Entreprise. Elle ne doit pas être ajoutée sous un autre intitulé.

## 7. TENDANCES ET ACTUALITÉ

En tête de section figure un paragraphe analytique de cinq à dix lignes maximum :

- produit à partir des signaux sourcés du compte ;
- synthétisant et interprétant la dynamique actuelle de l’entreprise ;
- distinguant obligatoirement l’observation factuelle de l’analyse.

Sous ce paragraphe figurent :

- les trois derniers signaux significatifs ;
- un accès à une modale listant tous les signaux.

La sélection des trois signaux privilégie leur significativité et leur actualité. Leur présence ne dispense jamais de conserver l’accès à la liste exhaustive.

## Règles transverses de sourcing

- FOLIO sert de référence de structure, de ton, de densité et de plan de recherche.
- Le contenu FOLIO historique n’est jamais une preuve suffisante.
- Un snippet de moteur de recherche n’est jamais une source finale.
- Toute URL citée doit avoir été réellement consultée.
- Chaque fait affiché doit être rattaché à au moins une source identifiable.
- Les chiffres critiques doivent utiliser une source officielle ou plusieurs sources indépendantes concordantes.
- Les analyses doivent être distinguées des faits.
- Les discours institutionnels doivent être identifiés comme déclaratifs.
- Les absences doivent être formulées prudemment.
- Une donnée contredite ou insuffisamment prouvée ne doit pas être publiée comme un fait.
- Les données relationnelles Kredo restent prioritaires pour les informations internes.
- Aucune donnée générée ne modifie automatiquement les champs canoniques de `companies`.
- Les enrichissements passent toujours par le mécanisme de propositions existant.

La conservation exhaustive des sources implique que la source consultée reste identifiable indépendamment de son utilisation dans une phrase particulière. La vérification indépendante doit produire une décision traçable : affirmation confirmée, contredite ou insuffisamment prouvée. Une contradiction ou une preuve insuffisante bloque la publication de l’affirmation comme fait.

## Priorité des données

1. Les données relationnelles Kredo/Supabase font autorité pour les informations internes et canoniques.
2. Les sources officielles consultées font autorité pour les faits publics directement vérifiables.
3. Plusieurs sources indépendantes concordantes peuvent étayer un chiffre critique lorsque la source officielle n’est pas disponible.
4. Les sources éditoriales ou professionnelles complètent le contexte avec une attribution explicite.
5. Les analyses générées interprètent les faits sourcés sans les remplacer.
6. FOLIO oriente le plan de recherche et la restitution, mais n’est jamais promu silencieusement au rang de preuve.

## Compatibilité et versionnement

- Les artefacts AccountKnowledge V1 et V2 restent lisibles.
- V3 constitue un nouveau contrat, discriminé explicitement par sa version.
- Aucune conversion rétroactive silencieuse de FOLIO, V1 ou V2 vers V3 n’est autorisée.
- Un artefact ancien non conforme à V3 reste affiché selon son lecteur historique ; il n’est ni réparé ni enrichi implicitement.
- Le type TypeScript V3 et son validateur runtime seront créés dans un lot ultérieur, jamais dans le Lot 0.

## Relocalisation future des blocs existants

Les blocs `Organisation`, `Activités opérationnelles` et `Relation commerciale` ne font pas partie du flux éditorial principal V3 et ne sont pas supprimés dans le Lot 0.

- `Organisation` doit rejoindre un espace relationnel consacré aux directions, interlocuteurs et données CRM, hors de l’étude générée.
- `Activités opérationnelles` doit rester rattaché au diagnostic process et à l’accès à l’audit complet.
- `Relation commerciale` doit rester rattachée à la timeline CRM, aux opportunités, aux engagements et aux contacts prioritaires.

Leur navigation et leur emplacement exact seront arrêtés avec la conception détaillée. Leur relocalisation ne doit entraîner aucune perte de données ni conversion en contenu généré.

## Vérification du socle Supabase

Le schéma réel a été vérifié en lecture seule le 4 août 2026. Les sept tables attendues existent et ont la RLS activée :

| Table | Capacité utile à V3 |
|---|---|
| `ai_intelligence_runs` | cycle de run, configuration, rattachement à l’entité et statut ; |
| `ai_intelligence_results` | contenu JSON versionné, texte, métadonnées, références de sources et drapeaux QA ; |
| `intelligence_sources` | identité, URL, URL canonique, dates, empreinte, extrait de preuve, fiabilité et méthode de collecte ; |
| `intelligence_source_links` | rattachement d’une source à un objet métier avec rôle du lien ; |
| `account_facts` | faits normalisés, origine, confiance, source primaire, dates de validité et état courant ; |
| `account_signals` | signaux sourcés, datés, scorés, dédupliqués et rattachés au run ; |
| `enrichment_proposals` | propositions versionnées, justifiées et soumises à décision avant application. |

Conclusion du Lot 0 : ce socle est suffisant pour figer le contrat fonctionnel V3. Aucune migration n’est indispensable et aucune migration n’est créée.
